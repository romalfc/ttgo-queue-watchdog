# Польовий чекліст TTGO Queue Watchdog

Перед виїздом результат кожної перевірки потрібно занести в журнал із часом, hash збірки та серійним номером пристрою.

## 1. Холодний старт і POST

**Що перевіряємо:** стабільність запуску після повного знеструмлення.

**Як перевіряємо:** 20 разів повністю вимкнути живлення на 10 секунд, увімкнути пристрій і дочекатися завершення POST у Serial Monitor. Виконати `version` після кожного запуску.

**Критерій успішного проходження:** кожен запуск завершується без зависання; POST mask дорівнює `0x0000000F`; watchdog не повідомляє про попередній інцидент; не відбувається неочікуваного повторного reboot.

## 2. Перевірка порожнього та відновленого NVS

**Що перевіряємо:** створення конфігурації за замовчуванням і збереження змін.

**Як перевіряємо:** очистити NVS, перезапустити пристрій, виконати `config get`; потім виконати `config set watchdog_timeout_ms 10000`, `config set duty_cycle_percent 2` і перезапустити пристрій.

**Критерій успішного проходження:** після очищення `cfg_version` дорівнює поточній версії, `watchdog_timeout_ms=5000`, `duty_cycle_percent=1`; після reboot зберігаються значення `10000` і `2`.

## 3. Перевірка меж конфігурації

**Що перевіряємо:** відхилення недопустимих значень без пошкодження чинної конфігурації.

**Як перевіряємо:** виконати команди `config set watchdog_timeout_ms 999`, `config set watchdog_timeout_ms 60001`, `config set duty_cycle_percent 0`, `config set duty_cycle_percent 101`, `config set log_level invalid`.

**Критерій успішного проходження:** кожна команда повертає помилку; `config get` показує попередні значення без часткового запису; після reboot значення залишаються незмінними.

## 4. Міграція конфігурації

**Що перевіряємо:** сумісність старого формату NVS із поточним форматом.

**Як перевіряємо:** виконати `config migrate 0.1`, перевірити reboot, потім виконати `config get`; після цього виконати `config migrate 0.2`, знову перезапустити пристрій і виконати `config get`.

**Критерій успішного проходження:** значення `serial_logging` і `watchdog_timeout_ms` не втрачаються; після автоматичної міграції під час старту `cfg_version=2`; повторний reboot не запускає міграцію повторно.

## 5. Перевірка OLED та cursor task

**Що перевіряємо:** роботу OLED і зміну інтервалу курсора.

**Як перевіряємо:** виконати `single-btn` для кожного переходу та виміряти інтервали між змінами стану курсора; виконати `double-btn` для переходу назад.

**Критерій успішного проходження:** послідовність інтервалів становить `100 -> 500 -> 1000 -> 2000 -> 100 мс`; подвійне натискання повертає на один крок назад; курсор не зупиняється під час LoRa-передачі.

## 6. Асинхронна LoRa-передача

**Що перевіряємо:** передача telemetry не блокує інші FreeRTOS-задачі.

**Як перевіряємо:** виконати `radio` 10 разів із паузою не менше 60 секунд, паралельно спостерігати cursor task і heartbeat watchdog; перевірити лог `LoRa TX`.

**Критерій успішного проходження:** кожна передача має payload 32 байти; `startTransmit()` і `finishTransmit()` завершуються без помилки; курсор продовжує перемикатися; watchdog не реєструє timeout.

## 7. Duty cycle 1%

**Що перевіряємо:** дотримання обмеження ефірного часу.

**Як перевіряємо:** виконати `radio`, виміряти `tx_duration` і час до наступного дозволеного запуску; перевірити повідомлення `Duty cycle` у debug-лозі.

**Критерій успішного проходження:** час очікування становить не менше `99 * tx_duration`; друга передача не стартує під час цього очікування; інші задачі продовжують виконуватися.

## 8. Watchdog і відновлення після зависання

**Що перевіряємо:** автоматичне виявлення deadlock і reboot із діагностикою.

**Як перевіряємо:** виконати `deadlock`, не натискати reset вручну, дочекатися перезапуску та прочитати Serial Monitor після старту.

**Критерій успішного проходження:** приблизно через 5--6 секунд з'являється watchdog-повідомлення; після reboot друкується попередній incident із причиною timeout, uptime, heartbeat, heap і core; пристрій знову завершує POST.

## 9. Добовий прогін

**Що перевіряємо:** стабільність роботи протягом тривалого часу.

**Як перевіряємо:** залишити пристрій увімкненим на 24 години, кожні 30 хвилин виконувати `version`, а кожні 60 секунд за наявності шлюзу запускати `radio` з дотриманням duty cycle.

**Критерій успішного проходження:** немає неочікуваних reboot; POST incident не з'являється; вільна heap-пам'ять не має монотонного падіння; ring log не містить повторюваних помилок; усі заплановані transmission мають очікуваний результат.

## 10. Перевірка роботи без шлюзу

**Що перевіряємо:** поведінку пристрою при відсутності приймача.

**Як перевіряємо:** вимкнути або віднести шлюз поза зону прийому, виконати `radio` 3 рази з дотриманням duty cycle, спостерігати watchdog і cursor task.

**Критерій успішного проходження:** локальна LoRa-передача не зависає назавжди; cursor task продовжує працювати; watchdog не спрацьовує через відсутність ACK, оскільки поточний протокол ACK не використовує; помилки RadioLib фіксуються в логові, якщо PHY їх повертає.
